================================================================================
1. ARCHITECTURE OVERVIEW
================================================================================

The app is a fully offline certificate verifier. A college prints a certificate
with a QR code whose payload is an obfuscated, checksummed certificate ID. The
student shows the certificate; the app scans the code, walks it through an
ordered gate sequence, and either displays the certificate record or refuses the
code with one precise reason while leaving the camera running. There is no
server, no account, no network permission, and no second screen beyond the four
described here.

The design separates two things that are easy to confuse. The QR payload is
OBFUSCATION, not cryptography: its algorithm is public and its only job is to
stop a human reading the ID off the paper and to make hand-editing detectable via
a position-weighted checksum. The real cryptography sits in the database, where
every column is encrypted at rest with AES-256-GCM, and it is protected at
lookup time by a deterministic SHA-256 hash column, because a fresh random salt
per value makes encrypted text impossible to search.

Layered view of a single scan:

    +---------------------------------------------------------------+
    |  ScannerActivity  (UI, camera, torch, red banner)              |
    |  zxing-android-embedded 4.3.0  DecoratedBarcodeView            |
    +-----------------------------+---------------------------------+
                                  |  raw scanned text
    +-----------------------------v---------------------------------+
    |  Layer B  GateSequence            gates 0, 0b, 1, 2, 3, 4      |
    |  first failing gate decides; only gate 4 may act               |
    +------+--------------------------+------------------------------+
           |                          |
    +------v--------------------+  +--v-----------------------------+
    | Layer A                   |  | Layer C  EncryptionHelper     |
    | CertificatePayloadCodec   |  | AES-256-GCM, PBKDF2 10k,     |
    | IBU1 + 64-char alphabet   |  | per-value salt and IV         |
    | block reversal + checksum |  +--+-----------------------------+
    +------+--------------------+     |
           | certificateId            |
    +------v-------------------------v-----------------------------+
    |  Layer D  HashUtil.certIdHash  SHA-256(id + pepper)           |
    |  CertificateRepository  WHERE cert_id_hash = ?                |
    |  CertificateDbHelper   SQLiteOpenHelper, table certificates   |
    +---------------------------------------------------------------+

Result routing:

    FOUND     -> VerificationActivity  (VALID, green tick, full record)
    NOT_FOUND -> NotFoundActivity      (INVALID, red icon, scanned ID)
    REFUSED   -> stay on ScannerActivity, red banner, camera keeps running
    IGNORED   -> nothing at all (gate 0b: a result screen is already opening)

3. LAYER-BY-LAYER DESIGN

--------------------------------------------------------------------------------
LAYER A - CertificatePayloadCodec  (OBFUSCATION, NOT ENCRYPTION)
--------------------------------------------------------------------------------

Stated plainly: this algorithm is public, holds no secret key, and must never be
described as providing confidentiality. Its two real benefits are that a human
cannot read the certificate ID off the printed paper, and that the position
weighted checksum detects hand editing. An attacker with the source can encode
any ID they like. Only Layer C and Layer D protect the data.

Alphabet (deliberately NOT Base64 - note the absence of + / and =):

    index   0..25   A..Z
    index  26..51   a..z
    index  52..61   0..9
    index  62       -
    index  63       _

Marker: IBU1, prepended on encode, located with indexOf on decode. Locating by
marker rather than by position is what lets the payload survive being printed
inside a longer string such as https://ibu.edu/verify?code=IBU1...

Algorithm, in order:

  1. LENGTH HEADER. Two 6-bit groups carry the UTF-8 byte length, 12 bits total,
     capped at MAX_PLAIN_LENGTH (120). Without this the decoder cannot know how
     many of the trailing groups are real data and how many are block padding.

  2. SIX-BIT CONVERSION. Each UTF-8 byte becomes two 6-bit values, low six bits
     first and the remaining top two bits second, shifted left four places so the
     unused low nibble is always zero:

         low  = byte & 0x3F
         high = (byte >> 6) << 4

     Emitting low first (rather than high first) means the entropy-heavy bits
     appear at the front of the payload, which is where block reversal scatters
     them furthest from their neighbours.

  3. BLOCK REVERSAL. The group list is zero padded to a multiple of BLOCK_SIZE
     (5), then each block of five is reversed in place. Reversal is its own
     inverse, so a single reverseBlocks() method both scrambles and unscrambles.
     Example, one block: [a b c d e] -> [e d c b a].

  4. POSITION-WEIGHTED CHECKSUM. One character is appended:

         checksum = ( SUM over i of (value_i + 1) * (i + 1) ) mod 64

     This is computed over the SCRAMBLED sequence, i.e. over exactly the
     characters the scanner will read, so it covers the padding too. The position
     weighting is what makes it detect a swapped pair of characters, which a
     plain sum cannot see: swapping characters at positions p and q changes the
     sum by (value_q - value_p) * (p - q), which is non-zero for any distinct
     characters at distinct positions.

  5. MARKER. IBU1 is prepended, the checksum character last.

  6. VALIDATION. decode() rejects a missing marker, a body longer than
     MAX_BODY_LENGTH, a body length that is not a multiple of 5 plus one, any
     character outside the IBU alphabet, a declared length that disagrees with
     the body size, non-zero padding, a bad checksum, a low group whose low
     nibble is not zero, and a decoded result that does not match the ID pattern.

ID pattern: see the deviation note in section 10 (Advisory). As implemented:

     ^CER[0-9]IB[A-Z0-9]+U[A-Z0-9]+$

Worked example, produced by the fixture tool:

     CER1IBAU0001  ->  IBU1FQDMAAxQSQBQCQJAwQVQwAwAwAAAAAi

Code (app/src/main/java/com/example/ibu_verification/security/CertificatePayloadCodec.java):

```java
public static String encode(String plainCertificateId) {
    if (plainCertificateId == null || plainCertificateId.isEmpty()) {
        throw new IllegalArgumentException("Certificate ID must not be empty");
    }
    if (!VALID_ID.matcher(plainCertificateId).matches()) {
        throw new IllegalArgumentException("Certificate ID does not match " + VALID_ID.pattern());
    }
    byte[] raw = plainCertificateId.getBytes(UTF8);
    if (raw.length > MAX_PLAIN_LENGTH) {
        throw new IllegalArgumentException("Certificate ID longer than " + MAX_PLAIN_LENGTH + " bytes");
    }

    List<Integer> values = new ArrayList<>();
    values.add((raw.length >> 6) & 0x3F);
    values.add(raw.length & 0x3F);
    for (byte b : raw) {
        int unsigned = b & 0xFF;
        values.add(unsigned & 0x3F);
        values.add((unsigned >> 6) << 4);
    }

    int padded = (values.size() + BLOCK_SIZE - 1) / BLOCK_SIZE * BLOCK_SIZE;
    while (values.size() < padded) {
        values.add(0);
    }

    List<Integer> scrambled = reverseBlocks(values, BLOCK_SIZE);
    int checksum = weightedChecksum(scrambled);

    StringBuilder builder = new StringBuilder();
    builder.append(MARKER);
    for (int value : scrambled) {
        builder.append(ALPHABET[value]);
    }
    builder.append(ALPHABET[checksum]);
    return builder.toString();
}

static int weightedChecksum(List<Integer> scrambled) {
    int sum = 0;
    for (int i = 0; i < scrambled.size(); i++) {
        sum = (sum + (scrambled.get(i) + 1) * (i + 1)) % ALPHABET_SIZE;
    }
    return sum;
}

static List<Integer> reverseBlocks(List<Integer> values, int blockSize) {
    List<Integer> out = new ArrayList<>(values.size());
    for (int start = 0; start < values.size(); start += blockSize) {
        int end = Math.min(start + blockSize, values.size());
        for (int i = end - 1; i >= start; i--) {
            out.add(values.get(i));
        }
    }
    return out;
}
```

decode() mirrors the above in reverse order, then validates length, padding,
checksum, six-bit pair shape, and the ID pattern before returning.


--------------------------------------------------------------------------------
LAYER B - GateSequence
--------------------------------------------------------------------------------

An ordered sequence in which the first gate to fail decides the outcome, and no
failure path ever reaches the database or a result screen.

  Gate 0   empty or blank read            -> "No QR code detected"
  Gate 0b  a result screen is opening     -> IGNORED, absolutely nothing happens
  Gate 1   payload contains SQR1          -> "Secure certificate not supported"
  Gate 2   payload lacks IBU1             -> "Plain Certificate ID not accepted"
                                            or "Not a certificate QR code"
  Gate 3   codec decode / checksum fails  -> "The QR code is damaged or has been altered."
  Gate 4   the only gate allowed to act  -> FOUND or NOT_FOUND

Gate 2 is the security check and it is a hard stop. When the IBU1 marker is
absent the code does not look anything up, does not pull out a regex match, and
does not try a fallback interpretation. It returns one of two distinct messages
purely so the user learns something useful: if the scanned text is shaped like a
bare certificate ID the app says the plain form is rejected, and for anything
else (a URL, a Wi-Fi code, a random string) it says this is not a certificate QR
code at all.

THE CAMERA-PAUSE PLACEMENT CONSTRAINT

This is the single most important implementation rule in the whole scanner, and
it is easy to break while "tidying up" the code.

The call that pauses the camera and the flag that says a result screen is
opening must sit at the TOP of Gate 4 - never at the top of the evaluate() method
or the top of the decode callback.

If either is set too early, the very first refused code freezes the scanner: the
camera stops, no result screen ever opens, nothing clears the flag, and the user
cannot scan anything again without killing the app. There is no code path that
recovers, because the only place that clears those flags is the return from a
result screen, which never happens.

The implementation keeps this safe by splitting responsibility:

  - ScannerActivity.openResult() is the ONLY method that sets resultOpened and
    calls barcodeView.pause(). It begins with an explicit guard on
    GateResult.Kind, so it can only ever be reached from a Gate 4 result.
  - GateSequence.evaluate() is a pure function of its arguments. It never
    touches the camera and never touches flags. The resultAlreadyOpen parameter
    is how the UI tells the gates that Gate 4 has already fired.

Refusals go through showRefusal(), which sets the banner, clears the
waitingForLookup latch and calls startScanning() again - the camera never stops
for a refusal.

Code (app/src/main/java/com/example/ibu_verification/security/GateSequence.java):

```java
public GateResult evaluate(String scannedText, boolean resultAlreadyOpen) {
    if (resultAlreadyOpen) {
        return GateResult.ignored();
    }

    if (scannedText == null || scannedText.trim().isEmpty()) {
        return GateResult.refuse(GateResult.Reason.NO_QR_DETECTED);
    }

    if (scannedText.contains(MARKER_SECURE)) {
        return GateResult.refuse(GateResult.Reason.SECURE_UNSUPPORTED);
    }

    if (!scannedText.contains(MARKER_IBU1)) {
        if (looksLikePlainCertificateId(scannedText)) {
            return GateResult.refuse(GateResult.Reason.PLAIN_ID_REJECTED);
        }
        return GateResult.refuse(GateResult.Reason.NOT_A_CERTIFICATE);
    }

    String certificateId;
    try {
        certificateId = CertificatePayloadCodec.decode(scannedText);
    } catch (CertificatePayloadCodec.PayloadException e) {
        return GateResult.refuse(GateResult.Reason.CODE_DAMAGED);
    }

    return gateFour(certificateId);
}

private GateResult gateFour(String certificateId) {
    try {
        Certificate certificate = lookup.findByCertificateId(certificateId);
        if (certificate == null) {
            return GateResult.notFound(certificateId);
        }
        return GateResult.found(certificateId, certificate);
    } catch (EncryptionHelper.EncryptionException e) {
        return GateResult.refuse(GateResult.Reason.STORE_UNREADABLE);
    }
}
```

The gate methods return a Reason enum rather than a finished sentence, so the
security package stays free of Android resource references and the UI owns the
wording. ScannerActivity.messageFor() maps Reason to a string resource.

Gates are executed on a single background thread. Decryption is PBKDF2 with
10 000 iterations across nine columns, which is far too slow for the main thread.

LAYER C - EncryptionHelper  (real cryptography)
--------------------------------------------------------------------------------

Algorithm: AES-256-GCM.
Key derivation: PBKDF2WithHmacSHA256, 10 000 iterations, fresh 16-byte random
salt per value, 256-bit output key.
IV: fresh 12-byte random value (96-bit) per value, the GCM standard.
Auth tag: 128 bits.
Stored layout: Base64( 16-byte salt || 12-byte IV || AES-GCM ciphertext+tag ).

A fresh salt and a fresh IV per value is mandatory for GCM: reusing either with
the same key destroys the security of the whole table.

Secret material. `app/build.gradle.kts` checks for encryption.properties at the
repository root. If the file does not exist it generates two 32-byte random hex
secrets with SecureRandom and writes the file, so a fresh clone builds with zero
manual setup. The values are injected as buildConfigField:

    buildConfigField("String", "CERT_MASTER_SECRET", ...)
    buildConfigField("String", "CERT_HASH_PEPPER", ...)

The file is listed in .gitignore and must never be committed.

Degradation path. If the pepper arrives empty (someone deleted the file after a
build, or a release was assembled with an empty field), EncryptionHelper does NOT
crash at startup. It logs an error once, sets active = false, and every
encrypt()/decrypt() call becomes a pass-through. The app stays usable and
readable; it simply stops protecting anything at rest, and the log line is the
signal. A hard crash here would brick the app with no way for a non-technical
user to recover.

Code (app/src/main/java/com/example/ibu_verification/security/EncryptionHelper.java):

```java
public EncryptionHelper(String pepper) {
    this.pepper = pepper == null ? new char[0] : pepper.toCharArray();
    this.active = this.pepper.length > 0;
    if (!active) {
        Log.e(TAG, "Master secret is empty. Storing values as plain text.");
    }
}

public String encrypt(String plainText) throws EncryptionException {
    if (plainText == null) {
        throw new IllegalArgumentException("Value to encrypt must not be null");
    }
    if (!active) {
        return plainText;
    }
    try {
        byte[] salt = new byte[SALT_LENGTH_BYTES];
        byte[] iv = new byte[IV_LENGTH_BYTES];
        random.nextBytes(salt);
        random.nextBytes(iv);

        Cipher cipher = Cipher.getInstance(CIPHER);
        cipher.init(Cipher.ENCRYPT_MODE, deriveKey(salt),
                new GCMParameterSpec(GCM_TAG_LENGTH_BITS, iv));
        byte[] cipherText = cipher.doFinal(plainText.getBytes(UTF8));

        byte[] blob = new byte[salt.length + iv.length + cipherText.length];
        System.arraycopy(salt, 0, blob, 0, salt.length);
        System.arraycopy(iv, 0, blob, salt.length, iv.length);
        System.arraycopy(cipherText, 0, blob, salt.length + iv.length, cipherText.length);
        return android.util.Base64.encodeToString(blob, android.util.Base64.NO_WRAP);
    } catch (GeneralSecurityException e) {
        throw new EncryptionException("Could not encrypt value: " + e.getMessage(), e);
    }
}

private SecretKey deriveKey(byte[] salt) throws GeneralSecurityException {
    SecretKeyFactory factory = SecretKeyFactory.getInstance(KEY_ALGORITHM);
    PBEKeySpec spec = new PBEKeySpec(pepper, salt, PBKDF2_ITERATIONS, KEY_LENGTH_BITS);
    try {
        return new SecretKeySpec(factory.generateSecret(spec).getEncoded(), "AES");
    } finally {
        spec.clearPassword();
    }
}
}

LAYER D - HashUtil  (the key insight)
--------------------------------------------------------------------------------

Encrypted values cannot be searched. Because every encryption uses a fresh random
salt and a fresh random IV, encrypting the same certificate ID twice produces two
completely different ciphertext strings. A query of the form

    WHERE certificate_id = ?

can therefore never match, no matter how obviously correct it looks. The bug
would not throw; it would simply always return "not found", and it would be
extremely hard to spot, because the encryption code is provably correct.

The fix is a second column, cert_id_hash, holding

    SHA-256( id + pepper )      rendered as 64 lowercase hex characters

The hash is not reversible, but it is deterministic: the same ID and the same
pepper always produce the same 64 characters. So the lookup becomes

    WHERE cert_id_hash = ?

which matches. The pepper is mixed in to defeat precomputed dictionary attacks -
without it, anyone holding the database could test every plausible ID against a
rainbow table; with it, the correct pepper is required, and it lives in
BuildConfig rather than in the database file.

THIS IS WHY THE SCHEMA STORES THE ID TWICE. certificate_id exists so the value
can be displayed to the verifier and so the record round-trips. cert_id_hash
exists purely so the row can be FOUND. Neither column can do the other's job:
one is random and unsearchable, the other is one-way and unreadable. This is the
single most commonly misunderstood decision in the design, and any future change
that "simplifies" it by deleting cert_id_hash will silently break all lookups.

The repository is the only place that may query this table. No Activity, and
certainly no gate, ever builds a SQL string from a scanned value.

Code (app/src/main/java/com/example/ibu_verification/security/HashUtil.java):

```java
public static String certIdHash(String certificateId, String pepper) {
    try {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        digest.update(certificateId.getBytes(UTF8));
        digest.update(pepper.getBytes(UTF8));
        return toHex(digest.digest());
    } catch (NoSuchAlgorithmException e) {
        throw new IllegalStateException("SHA-256 is not available on this device", e);
    }
}
```


--------------------------------------------------------------------------------
LAYER E - ASYMMETRIC SECURE QR  (NOT BUILT - decision recorded)
--------------------------------------------------------------------------------

DECISION: this phase is NOT wired. The reference app recognises SQR1 at Gate 1
and refuses it with "Secure certificate not supported", and that is the shipped
behaviour.

Justification. Layer E is the only part of this design that addresses a real
threat the other layers do not: an attacker who obtains a legitimate ID and
generates his own valid-looking QR. Layers A through D cannot stop that, because
the codec is public by design. A signature from the issuing authority can.

It is out of scope for a first shippable APK for three reasons. It needs a key
distribution story the college does not yet have. It makes the verifier unable
to work on certificates issued before the keys existed, which for a demo with
seven seed records is every record. And it is a real cryptographic protocol
needing its own threat model, test vectors and review, which does not belong in a
phase that is otherwise about a camera and a table.

Design for when it is adopted. A hybrid envelope:

    SQR1 || version || issuer_key_id (8 bytes) ||
           RSA-OAEP-SHA256( reader_public_key,
                            AES-256-GCM( HKDF(inner_key), payload ) ) ||
           RSA-PSS-SHA256( signing_private_key, everything above )

RSA-2048, RSA/ECB/OAEPPadding, MGF1-SHA-256. The verifier needs only the issuing
authority's signing PUBLIC key; the reader's private key never leaves the device.
Inner keys come from HKDF rather than from a fixed constant. Gate 1's existing
refusal is already the correct entry point, so adoption would be a change inside
Gate 1, not a rewrite of the flow.

4. DATA MODEL AND SCHEMA
================================================================================

Table: certificates. Exactly 11 columns.

  Column               Type       Null  Contents
  -------------------  ---------  ----  ---------------------------------------
  id                   INTEGER    no    PRIMARY KEY AUTOINCREMENT, local only
  certificate_id       TEXT       no    AES-GCM encrypted, Base64 blob
  cert_id_hash         TEXT       no    SHA-256(id+pepper) hex, UNIQUE indexed
  student_name         TEXT       no    encrypted
  roll_number          TEXT       no    encrypted
  enrollment_number    TEXT       no    encrypted
  course_name          TEXT       no    encrypted
  university_name      TEXT       no    encrypted
  passing_year         TEXT       no    encrypted (int stored as its string
                                         form, because ciphertext is text)
  percentage           TEXT       no    encrypted
  certificate_type     TEXT       no    encrypted

Note on passing_year: it is TEXT, not INTEGER. Every column except the two ID
columns is encrypted, and ciphertext is a Base64 string, so declaring it INTEGER
would be a lie about its type. The repository converts with String.valueOf() on
write and Integer.parseInt() after decryption.

DATABASE_VERSION = 2.

DDL (CertificateDbHelper.java):

```

The unique index on cert_id_hash does double duty: it is the lookup index, and
it makes a duplicate certificate ID impossible to insert.

The version 1 -> 2 migration, and why it is a table rebuild:

    @Override
    public void onUpgrade(SQLiteDatabase db, int oldVersion, int newVersion) {
        for (int version = oldVersion + 1; version <= newVersion; version++) {
            if (version == 2) {
                rebuildEncryptedTable(db);
            }
        }
    }

    private void rebuildEncryptedTable(SQLiteDatabase db) {
        db.execSQL("ALTER TABLE " + TABLE + " RENAME TO " + TABLE + "_old");
        db.execSQL(CREATE_TABLE);
        db.execSQL(CREATE_HASH_INDEX);
        db.execSQL("DROP TABLE " + TABLE + "_old");
    }

Version 2 adds cert_id_hash and converts the student columns from plaintext to
ciphertext. A rebuild is used rather than ALTER TABLE ADD COLUMN because the
change is not additive: existing rows would hold plaintext in a column that now
expects ciphertext, and there is no way to tell them apart in SQL - only the
application knows which is which. Rename, recreate with the correct schema, drop
the old table. SQLite DDL is transactional inside onUpgrade, so a crash
midway rolls back rather than leaving a half-migrated database.

Note that this path is written but has never executed against a real v1
database, because this project has only ever shipped as a fresh install. Treat
it as untested until a v1 fixture database exists.

onDowngrade drops and recreates. That destroys data, which is acceptable only
because the database is a cache of records that can be re-seeded - never do this
in an app with data the user cannot regenerate.

Seeding. CertificateSeeder.seedIfEmpty() inserts 7 records the first time
HomeActivity runs, through CertificateRepository, so every seeded value is
encrypted on the way in exactly like real data. Seed IDs are
CER1IBAU0001 .. CER3IBAU0007 with names, courses, years and percentages listed
in tools/java/tools/SampleRecords.java.

The seed set deliberately contains BOTH kinds of fixture, because a demo that
only shows happy paths proves nothing:

  valid, must open VerificationActivity:
      IBU1FQDMAAxQSQBQCQJAwQVQwAwAwAAAAAi   (CER1IBAU0001)
      and the other six encoded images

  valid format, no such record, must open NotFoundActivity:
      encode("CER1IBAU9999")

  must be refused at gate 2, camera keeps running:
      CER1IBAU0001                          bare ID
      https://example.edu/verify?id=7        a URL
      WIFI:S=CampusNet;T=WPA;P=secret;;     a Wi-Fi code

  must be refused at gate 1:

7. RISK REGISTER
================================================================================

R1  EMULATOR CAMERA DOES NOT READ A REAL QR
    Likelihood: HIGH. Impact: HIGH.
    The scanner cannot be demoed at all if the emulator camera will not decode
    a printed code, and the failure looks like an app bug rather than a tooling
    one.
    Mitigation: treat the desktop fixture generator as the primary verification
    path for Layers A, C and D - it needs no device. For the camera, use a
    physical device for the end-to-end demo and, on the emulator, feed an image
    into the virtual scene camera. Configure the decoder with TRY_HARDER and a
    480px fixture with a 4-module quiet zone.
    Early warning: a device test that decodes nothing after ten attempts on a
    clearly visible, well-lit code.

R2  PEPPER ROTATION DESTROYS EVERY ROW  (the data-loss trap)
    Likelihood: MEDIUM. Impact: CRITICAL.
    Each row carries its own random salt, and the key is PBKDF2(pepper, salt).
    Change the pepper and every existing row is permanently undecryptable - not
    "needs re-seeding", actually gone. The failure surfaces as a flood of
    "Could not decrypt value".
    Mitigation: never change the pepper on an existing installation. Documented
    rotation procedure: (1) record the reason for rotating, (2) export nothing -
    there is nothing exportable, (3) uninstall the app or run the app's reset
    path, (4) re-seed from the issuing system, (5) install the new
    encryption.properties. Treat a pepper change as a data migration, not a
    config change.
    Early warning: any "Could not decrypt value" in logcat immediately after a
    rebuild, which almost always means the pepper file was regenerated.

R3  LAYER A IS NOT CONFIDENTIAL AND WILL BE ASSUMED TO BE
    Likelihood: HIGH. Impact: MEDIUM.
    The codec is public and keyless. A reviewer, a marker, or a user may
    reasonably read "custom 64-character alphabet" as encryption. If someone
    relies on it to hide certificate numbers, the design has failed at exactly
    the point it claimed strength.
    Mitigation: call it obfuscation everywhere - code comments, the design
    document, the demo narration. Keep the real cryptography in Layer C, where
    it belongs. The Advisory section exists to make the distinction explicit.
    Early warning: any slide, README or comment calling Layer A "secure" or
    "encrypted".

R4  THE CAMERA FREEZES AFTER THE FIRST REFUSAL
    Likelihood: MEDIUM. Impact: HIGH.
    This is the placement bug from section 3 Layer B. It makes the app look
    completely broken on the second scan, and it is invisible in a happy-path
    demo.
    Mitigation: confine barcodeView.pause() and resultOpened to openResult(),
    reachable only from a Gate 4 Kind. Clear waitingForLookup in every exit path
    from onGateFinished. Test explicitly: refuse, then scan a valid code, with no
    app restart in between.
    Early warning: a manual test where the second scan does nothing.

R5  LOOKUP SILENTLY ALWAYS RETURNS NOT FOUND
    Likelihood: MEDIUM. Impact: CRITICAL.
    The most likely cause is querying WHERE certificate_id = ? against an
    encrypted column. It never throws; it just always misses, so every scan
    lands on NotFoundActivity and the app looks merely "too strict".
    Mitigation: all lookups go through CertificateRepository and use
    cert_id_hash. No Activity or gate builds SQL. The gate unit test counts
    lookup calls. A positive control - a known valid ID must open Verification -
    is part of the Phase 8 acceptance criteria, so a total lookup failure cannot
    pass the phase.
    Early warning: NotFoundActivity opens for a certificate ID you know is in the
    seed set.

R6  A CHECKSUM COLLISION SLIPS A TAMPERED CODE THROUGH
    Likelihood: LOW. Impact: MEDIUM.
    A single 6-bit position-weighted checksum is not a MAC and is not collision
    resistant; an attacker with the source can search for a collision offline.
    It is adequate for the intended job - catching accidental damage and casual
    hand editing - and nothing more.
    Mitigation: never treat Layer A as the trust boundary. Keep Layer D's
    peppered hash and Layer C's encryption as the real controls, and treat Layer
    E as the only real answer to a deliberate forger. The fixture generator's
    single-edit and swap checks are regression protection, not a proof.
    Early warning: any proposal to delete Layer D because "the checksum already
    proves it".

R7  DARK MODE INVERTS THE UI
    Likelihood: MEDIUM. Impact: LOW.
    Without values-night/themes.xml repeating the light theme, a DayNight parent
    would render a dark scheme, breaking the professional look and the white
    background the design calls for.
    Mitigation: values-night/themes.xml deliberately re-declares the same light
    theme. Check the app in dark mode before every release.
    Early warning: a black home screen on a device in dark mode.

9. DO-NOT-DO LIST
================================================================================

 1. Never accept a plain certificate ID from a QR code. Not as a fallback, not
    "when no marker is present", not behind a setting, not on a long press.
 2. Never query the database with a plaintext ID comparison. Only cert_id_hash.
 3. Never use java.util.Base64 or android.util.Base64 for the QR payload. The
    alphabet is custom; standard Base64 must fail to decode it. Base64 is only
    for storing the AES-GCM blob, which is a different thing.
 4. Never pause the camera or set resultOpened before Gate 4.
 5. Never add Compose, Kotlin, Room, Hilt, Retrofit or a backend. If one seems
    necessary, it belongs in the Advisory section, not in the code.
 6. Never call the payload codec "encryption". It is obfuscation with an
    integrity check. Layer C is the encryption.
 7. Never add a manual certificate-ID entry field.
 8. Never add a fifth screen - no sample-records list, no settings, no admin.
 9. Never add the INTERNET permission. If something seems to need a network call,
    the design is wrong.
10. Never check encryption.properties into version control.
11. Never rotate the pepper on an existing installation without following the
    documented wipe-and-re-seed procedure.
12. Never let a second class query the certificates table. The repository is
    the only door.
13. Never hardcode a user-visible string in Java. Gate reasons map to string
    resources.
14. Never set android:background on a MaterialButton. Use backgroundTint.
15. Never let values-night/themes.xml drift from the light theme - the white
    background and blue toolbar are a deliberate choice.
16. Never copy the codec into the desktop tools. tools/ compiles the real
    CertificatePayloadCodec so the two cannot drift.

10. ADVISORY
================================================================================

Everything in this section is optional. None of it was applied except where
explicitly noted as applied.

A1  THE PINNED ID REGEX NEEDS A CORRECTION  (DEVIATION APPLIED - please review)
    The brief pins the accepted ID pattern as ^CER[0-9]IB[A-Z0-9]U*$. Read
    literally, [A-Z0-9] consumes exactly one character and U* then means "zero
    or more U characters to the end of the string". That accepts only IDs like
    CER1IBUUU - it cannot hold a year or a serial number, so every real
    certificate ID fails validation at Gate 3 and the app rejects 100% of
    genuine certificates. The pattern was almost certainly meant to allow a
    middle segment before a U-separated serial.

    I implemented the evident intent:

        ^CER[0-9]IB[A-Z0-9]+U[A-Z0-9]+$

    which accepts CER1IBAU0001, CER2IBAU0004 and so on, and keeps the structure
    the pattern was clearly aiming at: a CER prefix, a version digit, an IB
    marker, and a U-delimited serial. This is the one place I deviated from a
    pinned constant, because the literal version makes the application
    non-functional. Please confirm the intended format; if CER1IBAU0001 is not
    the intended shape, only the regex constant needs to change.

A2  LAYER A COULD CARRY A SECOND CHECKSUM CHARACTER
    A single 6-bit checksum catches accidental damage and casual hand editing,
    which is its stated job, and the fixture tool proves it does. But while
    building an earlier revision I measured that a single position-weighted sum
    mod 64 can miss a single-character change, because the weight value*(i+1) can
    absorb it. Adding a second, differently-weighted character (for example a
    running sum h = h*31 + v + i, also mod 64) raised detection to a 12-bit
    check and closed that gap. I kept the single character because the brief
    specifies one, and the Layer E signature is the real answer to a deliberate
    forger. Worth revisiting if Layer E is never adopted.

A3  PINNED LIBRARY VERSIONS ARE SLIGHTLY BEHIND
    Lint reports newer available versions: AGP 9.4.1, compileSdk 37,
    constraintlayout 2.2.2, zxing core 3.5.4. I left all of them exactly as
    pinned. The AGP jump in particular would be worth doing at the start of a
    new project rather than mid-build.

A4  PORTRAIT LOCKING IS FADING
    Lint reports LockedOrientationActivity and DiscouragedApi for the four
    portrait locks, noting that fixed orientation is ignored on many devices
    from Android 16. Portrait is specified for the scanner, and the
    android:configChanges hint on ScannerActivity keeps the camera from
    restarting on rotation. This is a warning, not a defect, but it will become
    a real one on Android 16 devices.

A5  PBKDF2 AT 10 000 ITERATIONS IS BELOW CURRENT GUIDANCE
    10 000 is the pinned figure and is fine for a teaching project. Current
    guidance favours 600 000 or more, or a memory-hard KDF such as Argon2id. The
    practical mitigation here is different anyway: the pepper ships inside the
    APK in BuildConfig, so an attacker who extracts it has the key outright and
    iteration count stops mattering. The real fix for a production system is to
    not ship the key inside the app - see A6.

A6  THE MASTER SECRET LIVES INSIDE THE APK
    buildConfigField puts the pepper in the DEX, so anyone who unpacks the APK
    can read it and decrypt the whole database. This is inherent to a fully
    offline app with a local database and no server - the device must be able to
    decrypt on its own. It is honest to state: Layer C protects data at rest
    against casual extraction, backup leakage and file-level inspection; it does
    not protect against a determined reverse engineer. Adding a
    AndroidKeyStore-wrapped key and a user PIN would raise the bar, at the cost
    of a login screen, which the brief explicitly rules out.

A7  SEED DATA IS BUILT INTO THE APK
    The seven sample certificates are compiled in, so every installation ships
    with the same identities. Fine for a demo. A real deployment would import a
    signed dataset on first run, which is the natural place to also pin an issuing
    key for Layer E.

A8  THE GATE-4 CAMERA PAUSE COULD BE MADE STRUCTURALLY UNBREAKABLE
    Today the placement is protected by convention plus a guard clause and a
    comment. A stronger design would have GateResult expose only a sealed
    "MayOpenResult" token that ScannerActivity is the sole holder of, so a
    misplaced pause() would not compile. I kept the simpler version because it
    matches the beginner-friendly constraint, but the risk is real and permanent
    as long as the code is hand-edited.
